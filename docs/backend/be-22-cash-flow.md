# BE-22 prospective cash reporting

The new MANAGER-only `/api/v1/manager/finance/cash-flow/{overview,trend,breakdown,export}` routes report system-recorded collections and completed refund payouts by event period. They do not assert independent bank settlement. Legacy overview/trend/transactions/revenue/export semantics remain unchanged. FE-13 needs a separate cash-flow adaptation and browser acceptance.

V31 installs an inactive `cash_coverage` singleton, `cash_capture_ticket` and append-only `cash_event`. No history is imported. UTC event/cutover columns are DATETIME2(7); the application writes exact microseconds from its injected Clock. Existing payment_time remains local DATETIME2(0) and is never reinterpreted for the new report. Reporting bounds use Asia/Ho_Chi_Minh inclusive date start / exclusive next-day start converted to UTC. Net is gross collections minus completed payouts, and may be negative. Original collections survive SUCCESS -> REFUNDED. Approval/rejection are not payouts; BE-21 still allows one completed refund per payment, including partial refunds.

## Controlled activation

Do not run migration or monetary requests against an existing database as part of review. After independent review and mandatory SQL CI, a deployment owner should drain old writers, apply the forward migration normally, and deploy the upgraded application. Set `app.finance.cash-capture-enabled=true` (environment `APP_FINANCE_CASH_CAPTURE_ENABLED=true`) for explicit activation on its first successful instrumented monetary transaction. Default false preserves inactive deployments. The first transaction establishes cutover from application Clock and records its event atomically; rollback rolls back both. A report before activation returns unavailable. Turning the local setting off after durable activation does not stop capture.

Database source triggers require a transaction-bound Clock ticket after activation and create the event in the source transaction. Tickets use CURRENT_TRANSACTION_ID(), never pooled session state. Inactive source writes hold a marker lock until commit so activation cannot overtake them. Older instances/direct uncovered writes are rejected after activation. Event/active-marker mutation or deletion and direct manual event insertion are rejected. A failed event write rolls back the monetary transition. Normal application grants must not permit disabling triggers or altering this schema; privileged database tampering is outside the completeness guarantee and requires an integrity incident review, not automatic reactivation or guessed repair.

First activation may block behind in-flight transactions; drain older writers to avoid old-version monetary failures and lock contention. SQL Server deadlock/timeout rollback does not create a cash event or a successful uncovered transition; use existing application error/retry behavior. App Clock must be synchronized and must not precede cutover. Coverage is the database's application-authoritative source stream as of the response's `asOf`; it is not a forecast of future cash or bank reconciliation.

## Coverage and API

`overview?month=yyyy-MM` defaults to the business current month. `trend?months=N` defaults to 6, accepts 1..24 and rejects the entire trend if any requested month is unverified. `breakdown?from=yyyy-MM-dd&to=yyyy-MM-dd&groupBy=ITEM_TYPE|METHOD|SPORT` and `export?from=...&to=...` use existing finance limits: inclusive dates 1900-01-01..9999-12-30, at most 366 days; default month-start through today. Overview whole months must fit those bounds. Invalid parameters are 400. Anonymous is 401; MEMBER/COACH/RECEPTIONIST are 403.

Any inactive, pre-cutover, cross-cutover or currently unguarded interval returns 409 with code CASH_HISTORY_UNVERIFIED and safe coverage details. No partial month/day is presented as a full zero period. A fully covered empty interval returns zero with VERIFIED_COMPLETE. Monthly reports for the activation month will normally be unavailable; select a fully covered date range after cutover. A post-cutover payout against an older collection is valid cash-out only; no old collection is manufactured.

Overview and trend points contain month/from/to, grossCashReceived, completedRefundCashOut, netCashFlow, collectionCount, completedRefundCount and coverage {status,coverageStart,timeBasis,timezone,evidenceBasis,asOf}. Breakdown has the same totals, bounds/groupBy/coverage and rows with key/label plus those five metrics. Monetary values are exact BigDecimal/SQL DECIMAL sums; no growth percentage is invented or exposed.

Collection snapshots use proven original method and a unique persisted item/sport link agreeing with any existing invoice lines. New desk payments may precede persistence of their item link; those unknown dimensions are permanently UNALLOCATED. Payout copies a recorded original collection snapshot, otherwise missing historical/null linkage is UNALLOCATED. Attribution is original collection method, not a claim about refund transfer method. Every event contributes exactly once to each grouping; grouped totals/counts must reconcile or the report fails. Later invoice/source changes cannot rewrite snapshots.

CSV is authenticated, UTF-8 BOM, CRLF, ordered by UTC event time then immutable ID, with filename cash_flow_FROM_TO.csv. Columns: event_id,event_time_utc,event_type,payment_id,refund_request_id,amount,cash_impact,provenance,original_method,original_item_type,original_sport_key,original_sport_name. Missing source IDs are blank; unknown attribution is UNALLOCATED. No member names, contact details or bank reference are exported. Text uses the established formula/quote/control-prefix guard. Preflight plus actual bounded stream enforce 50000 events with no partial attachment. Stream gross/payout/counts must match SQL aggregate totals.

## Required verification before rollout

Run backend `mvn -B -ntp verify` on a Docker-enabled runner, unit/integration report guards and zero-skip checks. The required SQL manifest includes CashEventIntegrationTest and CashMigrationIntegrationTest, exercising real BE-21/service/API synthetic flows, fresh/demo/upgrade V30 -> V31, activation concurrency, UTC precision, duplicate/rollback, immutability and SQL/API/group/CSV reconciliation. Local unit and parser tests cannot substitute for those gates. All monetary tests create disposable data inside new SQL Server Testcontainers lifecycles. No retained acceptance database or real refund is involved.

SQL Server references: [CURRENT_TRANSACTION_ID](https://learn.microsoft.com/en-us/sql/t-sql/functions/current-transaction-id-transact-sql) and [OUTPUT clause](https://learn.microsoft.com/en-us/sql/t-sql/queries/output-clause-transact-sql). OUTPUT without INTO is incompatible with enabled source triggers; affected SQL test identity helpers now use OUTPUT INTO, without weakening their assertions.

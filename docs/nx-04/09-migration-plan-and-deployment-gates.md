# Migration plan and deployment gates

Status: BLOCKED_PENDING_APPROVAL. This is a numbered forward-only design plan; no SQL is executable in this package. Runtime migration tests are NOT_RUN_APPROVAL_BLOCKED. An isolated disposable non-Docker SQL Server has not been established. Never use the default dev datasource or a shared local DB as a test target.

The reuse audit demonstrates actual gaps requiring additional storage if the complete personal/class, revision, attribution and private-note options are adopted. V16 already stores current class plans, attendance, results and feedback, so recreating them wholesale is unjustified. No new table is needed merely to preserve the existing Receptionist arrival service. Which additional tables/columns are necessary depends on the signed Option A/B choice, not the existence of a design document.

## Gated implementation sequence

1. **Adoption and semantics gate.** Obtain D-11/G-00, D-01, D-02/03/12/13 parent and every required dimension, or signed scope-specific deferrals. Select plan identity, audience, historic entitlement, metric governance, correction mechanism and current attendance identity. Name the actual business/privacy authorities. Resolve D-10/G-01 wire and FE projection contracts.
2. **Specific physical gate.** Review dictionary, candidate PK/FK targets, NULL/XOR rules, visibility storage, immutable content, types/precision and index definitions. Dat/CODEOWNER sign an exact version/hash and scope. This approval must precede migration or mapping code, and does not authorize unrelated APIs. Retention/backfill semantics and deployment/recovery owners are separately recorded.
3. **Fresh source reconciliation.** Fetch origin with prune, record main SHA, merge main into the clean task branch without rewriting published history. Re-enumerate migration versions across standard and demo locations, immutable checksums and new objects. Current maximum is V33; do not reserve V34 now. Allocate the next nonconflicting global version at coding time; never fill old gaps with out-of-order disabled or edit an old migration. Re-run source guards after any upstream change.
4. **Disposable environment gate.** Owner supplies explicit test-only host/DB allowlist, unique per-run database names, least privilege, SQL Server version/collation/isolation, credentials through approved secret channel and teardown responsibility. Prove empty disposable identity and reject shared/prod/unknown names before connection. No live DB inspection/backfill is permitted by this task. CI's isolated SQL Server containers are a later authorized runtime, not a reason to run Docker locally.
5. **Read-only profiling on the approved disposable copy.** Measure existing pair duplicates, result metric duplicates, NULL booking links, orphan candidates, booking/session/member mismatches, class-only plans, missing actors, invalid/unknown correction status text, actual timestamp provenance and text lengths. Report counts and samples with minimized identifiers. Confirm constraints/indexes through system catalogs, not only this static census. No fabricated counts or automated data repair. Production profiling requires new explicit authorization.
6. **Additive expansion.** Implement only the approved subset: candidate plan identity/revision/assignment/use, result/feedback revisions and required guard metadata; reuse existing current identities and FKs. Initial optional compatibility columns can remain nullable until signed backfill is complete. New mandatory fields need either an approved deterministic source or a separately reviewed phased constraint. Keep legacy readers working, and do not expose new fields before authorization/projections are ready.
7. **Backfill only if approved and necessary.** Separate reviewed migration or bounded operational job with deterministic keys/checkpoints and repeat-safe behavior. Legacy class plans cannot become personal assignments or published revisions by inference. Original result Coach author is absent; do not fabricate one from current session Coach. Do not derive attendance from arrivals/ACKs, infer Member entitlement from every booking, label legacy local time UTC, or seed metrics/rating policy from scaffold defaults. Quarantine/report unresolved data under an approved disposition.
8. **Constraint and index enforcement.** Prove selected candidate keys against measured distributions. Resolve duplicates through approved attribution/history handling rather than deleting rows. Validate FKs with existing rows, same-parent revision chains, target XOR and agreed non-null values. Test the nullable UNIQUE/filtered index/collation cases on SQL Server. Review transaction boundaries, Flyway handling of GO/batches, possible lock escalation, index build options supported by the actual edition, and timeout policy before any larger build.
9. **Compatibility and failure rehearsal.** In disposable databases test fresh full migration chain, upgrade from preceding source baseline, latest schema with old application readers, new mappings with validate, empty/legacy fixtures, repeat migrate no-op, interrupted phase and forward correction. Existing Flyway checksum history must remain identical. Test demo opt-in and prod+demo refusal. Required Flow 1-3 booking, check-in and payment invariants must remain green, with zero training-induced finance changes.
10. **Deployment decision.** Review measured lock duration, row counts, migration history, failure logs, security tests and rollback drill evidence. No lock-time estimate or backup capability is asserted here. CODEOWNER/environment owner signs deployment order, maintenance needs and stop conditions. Deploy additive schema before dependent application code; enable training only after schema/contract/RBAC checks. Avoid dual writers unless a separately reviewed atomic protocol exists.
11. **Post-deploy verification under separate authorization.** Compare selected constraints/indexes, Flyway validation, old/new read compatibility and approved minimized reconciliation counts. Stop rollout on unexpected cardinality, scope leakage, orphan/mismatch, missing audit/history, double debit or incompatibility. Preserve evidence without exporting private narratives.

## Partial failure and version hygiene

Flyway transaction behavior depends on SQL Server statements and configuration; do not assume every phased migration is atomic. For a failed migration, stop subsequent deployment, inspect the actual schema/history and classify whether its transaction rolled back or effects remain. A failed history repair, if necessary, requires owner-reviewed recovery after schema reconciliation. Never use repair to conceal an edited checksum. `clean` remains disabled, and success is not established by adding IF NOT EXISTS around an unknown partial object. Compare full definition and expected data before deciding a corrective migration.

Every versioned file is immutable after publication/application. If main receives overlapping work, regular merge and version reallocation happen before new migration publication; if a version is already deployed, use a fresh forward corrective migration. Do not delete history, reuse an applied version or put demo credentials/data into standard migrations. Schema-only review and documentation CI cannot open deployment gates.

## Maintaining the source guard for future approved work

The source inventory is an exact, review-maintained census, not a permanent ban on additive migrations. The static guard checks SQL path population, LF-normalized SHA-256, versions and CREATE TABLE census against `source-inventory.json`. It cannot verify a human signature. An inventory update is not migration authorization, and an unchanged inventory intentionally rejects an unreviewed new SQL file.

The owner of a future feature updates this inventory in that feature's ordinary reviewed PR, after obtaining the migration and feature approvals required for its own scope. The repository CODEOWNER reviews that diff under the existing CODEOWNERS rules. There is no additional NX-04 owner sign-off for unrelated features. Flow 4 work still requires every signed gate above; maintaining this census cannot open those gates.

1. Fetch and integrate current main safely. Reconcile any already approved upstream additions before running this exact-population guard; do not disable the guard to unblock an advancing main.
2. Preserve all existing migration paths, versions, fingerprints and SQL bytes. Append the newly authorized migration's exact path, globally nonconflicting next version, LF-normalized SHA-256 and declaration metadata. Update aggregate CREATE counts/names for the resulting full source population. If approved work adds JPA entities or moves referenced definitions, reconcile those separate census/reference entries and affected design observations explicitly in the same review.
3. Keep the historical `baseline` and its source observations identified as historical. Document the current-main SHA, migration authorization and exact inventory diff in the feature PR. A refreshed source baseline or changed design observation must be an explicit reviewed correction, not an automatic overwrite of historical evidence.
4. Run the static guard and shared Python suite, then the existing PR Flyway migration guard against current main. `scripts/ci/check-migrations.sh` independently rejects modification, rename or deletion of already merged migrations, duplicate versions and additions at or below main's maximum. Changing an old fingerprint in the inventory cannot bypass that Git-based check. Never auto-regenerate historical hashes to bless SQL edits.
5. Obtain ordinary CODEOWNER acceptance before merge. If main advances again, repeat reconciliation and exact-head CI. An approved upstream migration is accounted for by the same append-only census update; a stale census is a reviewable maintenance change, not a permanent CI deadlock or an implicit veto by NX-04.

The sensitivity suite simulates this workflow entirely in memory with a synthetic additive CREATE TABLE and an exact appended inventory entry. Its positive control passes, while historical edits/deletions, new-file fingerprint drift and a stale CREATE census still fail. No fixture SQL is written or authorized for deployment. The guard and the separate PR migration check remain enabled without exceptions or workflow permission changes.

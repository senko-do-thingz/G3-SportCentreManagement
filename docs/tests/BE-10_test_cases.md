## Interpretation and limitations

The UI provides screenshots rather than a machine-readable API specification. This API uses the prompt's field names and nested resources for the conflict screen. The availability button uses no separate new endpoint in this task. Single creation returns the same array shape as weekly creation.

The limits of 62 inclusive calendar days and 100 generated sessions, DRAFT resource occupancy, no edit/cancel after start, edits with bookings without notifications, and 400 on repeated cancellation are implemented assumptions. SELF_TRAINING permits no coach as shown by F2-02. Incomplete drafts, standalone self-training creation, recurrence series editing, facility capacity/sport rules, notifications, waitlist changes and monetary refunds remain outside scope.

Resource locks protect BE-10 scheduling writers on the same database. Waiting follows the existing unbounded locking convention; SQL Server deadlock victims get retry guidance. Legacy individual booking/cancellation counters do not follow the same protocol, so general booking concurrency remains outside scope. A linked package registration is treated as evidence of one consumed session; no separate consumption flag exists. Restoration uses its total_sessions snapshot and preserves registration status.

MANAGER has all four endpoints. Other authenticated roles receive 403. Anonymous requests receive 401 under the existing project convention. Calendar filters are selectors, so unknown filter ids return an empty list instead of 404. GET and cancellation do not have business schedule-overlap 409 cases; POST is the only 201 operation.

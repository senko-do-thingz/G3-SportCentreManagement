## Interpretation and limitations

The UI provides screenshots rather than a machine-readable API specification. This API uses the prompt's field names and nested resources for the conflict screen. The availability button uses no separate new endpoint in this task. Single creation returns the same array shape as weekly creation.

The limits of 62 inclusive calendar days and 100 generated sessions, DRAFT resource occupancy, no edit/cancel after start, edits with bookings without notifications, and 400 on repeated cancellation are implemented assumptions. SELF_TRAINING permits no coach as shown by F2-02. Incomplete drafts, standalone self-training creation, recurrence series editing, facility capacity/sport rules, notifications, waitlist changes and monetary refunds remain outside scope.

Resource locks protect BE-10 scheduling writers on the same database. Waiting has no timeout and can hold a database connection. Pessimistic lock failures inside the service body get retry guidance; exceptions raised at transaction commit can still become 500 because they occur outside withLockHandling. Capacity cannot go below the confirmed bookings counted at update time, and updates do not repair cached booked_count. Booking creation locks the session before checking status/capacity; individual cancellation resolves a scalar session id, locks the session and only then loads the booking entity. This closes the create/cancel race with manager cancellation and prevents a second refund for an already cancelled booking. The initial registration snapshot is not locked, but consumption uses a conditional SQL decrement requiring a positive balance, ACTIVE database status and inclusive session-date validity. Exactly one affected row is required. A zero-row result returns an existing status/date/balance error before session or booking mutations. Individual cancellation uses capped ACTIVE-only SQL restoration. These commands serialize on the registration row with the existing manager refund UPDATE. The remaining_sessions mapping permits initial INSERT but prevents stale JPA entity saves from overwriting the database balance. No registration balance read/modify/save remains in booking creation or cancellation. Unit mocks do not establish transaction rollback; the real-database cases below cover it.

When confirmed bookings exist, one set-based validity count rejects dates outside any linked registration's inclusive start_date/end_date range before assignment locks. Null package links are ignored. Time-only and coach changes remain allowed; this assumption requires product owner confirmation.

A linked package registration is treated as evidence of one consumed session; no separate consumption flag exists. Only ACTIVE registrations receive credits, capped at the purchased total_sessions snapshot. All CONFIRMED bookings are cancelled regardless of registration status; non-ACTIVE balances and registration statuses remain unchanged. The repository unit test verifies SQL bindings and execution order using a mock, not actual SQL Server refund execution. The registrations audit array contains registrationId and packageBookings, which describe linked confirmed bookings before cancellation rather than restored credits. Null links are excluded from the list but included in bookingsCancelled. Real status-dependent effects and audit serialization remain covered by the unexecuted integration suite.

The conflict response retains requestedDate even though it equals date, preserving the existing contract. The message is "The selected coach, facility or time conflicts with existing sessions. Choose another coach, facility or time." DRAFT has no publication endpoint, so it is not bookable until a separate publication policy is implemented. A weekly batch containing a selected occurrence today whose start has passed fails closed with 400; it does not skip that date. V23 is unchanged because it was already shared; a same-name index with different columns remains a documented migration risk.

MANAGER has all four endpoints. Other authenticated roles receive 403. Anonymous requests receive 401 under the existing project convention. Calendar filters are selectors, so unknown filter ids return an empty list instead of 404. GET and cancellation do not have business schedule-overlap 409 cases; POST is the only 201 operation.

V23 is unchanged. A same-name index with different columns, or a local database that already applied V23, can still conflict. No timeout policy or migration repair is introduced. A project-wide lock timeout decision shared with BE-03 remains a follow-up. A weekly batch that includes today with its start already reached fails as a whole with 400; it does not skip that occurrence. DRAFT sessions still have no publication endpoint; this is an open product owner question.

Shared-registration concurrency cases use separate transactions/connections, preloaded snapshots, bounded latches/futures and SQL Server DMV polling of the exact blocked registration UPDATE. A test-only no-op registration UPDATE is held before booking writes so unrelated booking-row read blocking cannot hide the contested balance. The container uses sa and the helper asserts sysadmin visibility. Writer transaction timeouts are test-only; production lock waits remain unbounded. These cases exercise the refund-first interleaving for individual and manager cancellation. They do not prove every consume-first/refund-first scheduling order or absence of deadlocks, lock escalation or multi-registration cancellation deadlocks. No Thread.sleep or Disabled annotation is added.

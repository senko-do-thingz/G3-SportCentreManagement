# Flow 1-4 release migration review

Release additions are V42 explicit class plan scope, V43 durable arrival passes, V44 class notices, V45 general support intake and V46 notification origins. Existing upstream scripts are unchanged. Upstream PR 193 introduced opt-in demo V41 while this branch was in progress. The branch-only class plan and arrival additions were renumbered before release to avoid that collision. Existing test databases retain their original histories and are not reused, repaired or cleaned. No protected database has applied these additions.

V42 defaults every historical plan to INDIVIDUAL. A null historical Member never grants class visibility. V45 leaves historical training tickets with null intake fields, so the general support APIs exclude them. V46 leaves existing notifications with null event origin; owner access remains unchanged. No membership tier migration is needed for CREATE because current constraints, locks and service validation are reused.

The owner should authorize the exact target, verify a restorable backup and capture the selected database, existing Flyway history/checksums and application build identity. Review `scripts/maintenance/Flow1-4-Release-Preflight.sql` before executing it. It contains read-only metadata/count queries and has not been run against protected databases. Review all new constraints and version uniqueness, including optional demo locations. Test a backup restored to a new isolated name before approving any runtime activation. Continue using the existing single datasource and Flyway configuration; do not activate the demo profile on a protected runtime.

Application rollback should stop the new write paths and restore the prior approved binary while retaining additive schema and audit/history. Rehearse rollback on the isolated backup restore. Do not drop columns/tables containing new history, rewrite applied SQL, repair/baseline Flyway or run clean as a rollback. If an application migration fails, stop activation and involve the database owner; do not repair a protected target automatically.

Native SQL test harnesses require an explicit loopback port and test credentials, create a unique owned `sportify_unify_test_` database and disable AUTO_CLOSE only on that newly created fixture. They never fall back to inherited application DB_URL. Historical finance compatibility cases retain their explicit migration targets and validate unchanged checksums. Container lifecycle unit tests remain available for the Docker path.

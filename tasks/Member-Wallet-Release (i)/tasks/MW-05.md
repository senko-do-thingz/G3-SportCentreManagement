# MW-05 - Wallet Settlement / Booking Safety - ONE PR

**PR title:** `fix(flow-2): integrate wallet settlement with safe booking`
**Depends on:** MW-04.

## Scope
- Reuse existing paid products (sport packages, membership cards, and supported one-time visit if implemented) to accept wallet as an INTERNAL funding source. Do not invent a per-session price or a new external payment channel.
- Wallet payment, package activation and invoice/payment reference should commit together; under wallet insufficient funds or validation error, no partial purchase/entitlement. Preserve `CASH`, `BANK_TRANSFER`, and QR alternatives.
- Existing Session Booking generally consumes package session credits, NOT more VND. Two simultaneous bookings for the last seat -> max one success; loser retains package credits and wallet balance. Cross-flow service and database transaction ordering must prevent overbooking and overspending.
- If a true separately priced single-session booking exists, integrate charge + seat reservation atomically. On unexpected committed wallet debit + failed seat, create exactly-once compensating wallet credit tied to original debit, otherwise just roll back without fake refund. For an already-paid package whose requested class is full, do NOT refund package purchase automatically.
- Preserve duplicate booking and existing same-day arrival/check-in/cancellation/credit restoration invariants; add negative concurrency tests.

## Acceptance
1. Wallet-funded eligible purchase succeeds once; duplicate call never double-debits or double-activates entitlement.
2. Wallet cannot go negative. Existing cash/bank/QR purchase still works.
3. Concurrent last-seat Booking prevents overcapacity, double package-credit consumption and any unintended wallet credit.
4. Member sees understandable full-class/no-charge result. Compensation (if applicable) is visible and auditable.

## Evidence
- Screenshot A: real Desktop UI selecting Wallet for an eligible existing service purchase / success.
- Screenshot B: full-class booking denied with unchanged wallet, or linked exactly-once compensation if a captured charge scenario exists.
- Screenshot or test artifacts for two-user race (one success/one reject), with DB verification separately.

## Explicit dependency decision
If current repo does not have standalone paid individual class booking, wallet does *not* directly purchase a seat. It purchases existing packages/visits; Booking still consumes eligible package sessions. Do not silently build a new price/payment model.

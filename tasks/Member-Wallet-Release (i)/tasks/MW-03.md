# MW-03 - Wallet Core / Ledger / Overview - ONE PR

**PR title:** `fix(flow-3): implement internal wallet ledger and overview`
**Depends on:** MW-02.

## Scope
- Introduce one internal wallet per Member, stored in `sportify` with explicit provenances (real confirmed vs simulated demo); use exact VND amounts, DB-level constraints/locks, append-only ledger, unique operation references and idempotency. No wallet cross-account move, negative wallet, manual arbitrary credit or fake successful bank transfer.
- Support available balance and reserved balance (when withdrawal later implemented), provider/amount provenance and an authoritative per-member ledger read API; wallet should be a *separate subdomain* from standard Cash/Bank/QR payments and existing package refunds.
- Introduce Member Wallet Overview Desktop page showing available/reserved balance, last activity (empty initial state) and demo label. Backend owns balance math; frontend must not compute an authoritative balance from arbitrary client rows.
- Implement unit tests for concurrency, identical idempotency key, precision/bounds, role-based access, invalid amount, simulated-provenance exclusion from actual financial reports.

## Acceptance
1. A fresh Member wallet exists/initializes safely with zero balance and correct provenance; no unexplained money can appear.
2. All balance changes are represented by exactly-once, immutable ledger records. Non-member cannot query another Member wallet.
3. Existing payment and refund services are unchanged or safely integrated; finance reports still distinguish actual money.
4. DB migration is additive and requires owner authorization before applied to shared `sportify`.

- Screenshot B: no-transactions state or protected denied request/insufficient funds shown in real desktop UI.
